# Заявки сайта через Cloudflare

Ветка `codex/cloudflare-form-mail`. Бизнес-панель не используется. Форма отправляет имя, телефон и необязательный комментарий на `/api/leads`.

## Что считается приёмом заявки

HTTP 202 возвращается только после записи в D1. Повтор того же запроса с тем же UUID не создаёт новую запись. Если сеть оборвалась, посетитель повторяет отправку с сохранённым в памяти страницы UUID. После перезагрузки страницы это уже новая попытка: персональные данные в браузерное хранилище не записываются.

Worker отправляет письмо на `gerasim459@gmail.com` через ограниченный `send_email` binding от `requests@zeez.co.il`. Подтверждённый адрес получателя позволяет использовать отправку Email Routing без платной подписки Email Sending. Адрес получателя невозможно изменить из формы. Тело письма текстовое; поля пользователя не попадают в заголовки или HTML.

Отправка начинается сразу после сохранения. Каждые две минуты Cron подбирает до 10 готовых записей, включая незавершённые попытки с истёкшей двухминутной арендой. Повторы: 1, 2, 4, 8 минут и далее до интервала 6 часов. Сохранённые заявки не удаляются при ошибке отправки. Записи со статусом `mail_accepted` удаляются через 30 дней после принятия письма почтовой службой.

`mail_accepted` означает принятие Cloudflare, **не доказательство попадания во входящие Gmail**. Возможны спам, поздний отказ сервера получателя, отключённый Gmail и аварии Cloudflare. Не существует 100% гарантии доставки. При обрыве между отправкой письма и записью статуса возможно повторное письмо: его отличает тот же номер заявки. Это предпочтительнее потери обращения.

## Защита

- Статические страницы обслуживаются без вызова API Worker; обработчик запускается только для `/api/*`.
- Проверяются точный Origin, hostname, метод POST, JSON и размер тела не более 8 КиБ, включая поток без Content-Length.
- Turnstile проверяется на сервере: подпись токена, hostname и действие `booking`. Недоступность защиты приводит к отказу, а не обходу.
- Грубое ограничение IP: 20 запросов в минуту на расположение Cloudflare. Это не абсолютный глобальный лимит; мобильные сети разделяют IP.
- Атомарные ограничения D1: 3 новых заявки с одного телефона в час, 200 новых заявок в час всего, до 1000 неотправленных записей. При достижении лимита форма показывает ошибку, а ранее принятые заявки сохраняются.
- SQL только с параметрами. Список полей, типы и длины ограничены. Публичного чтения заявок и публичной админки нет.
- Секрет Turnstile хранится только в секрете Worker. В логи не записываются имя, телефон, комментарий, токен или полные ошибки поставщика.
- D1 и токены аккаунта доступны только владельцу через Cloudflare. Новые операторы/интеграции не добавляются.

Бесплатный тариф имеет лимиты Workers и D1; массовая атака может исчерпать их. Защита снижает риск, но не делает сервис неуязвимым. Следить за лимитами, ошибками и задержками нужно и после запуска.

## Подключение

1. Email Service → Email Routing: домен `zeez.co.il` должен стать Enabled, Gmail — Verified. Не заменять MX другого почтового сервиса без проверки.
2. Создать отдельную D1 `zeez-site-leads`; её ID вписать в `wrangler.jsonc`.
3. Создать Managed Turnstile widget только для `zeez.co.il`, `www.zeez.co.il` и `mazganim-clean-air.gerasim459.workers.dev`. Публичный site key записать в `vars.TURNSTILE_SITE_KEY`. Секрет вводить через `wrangler secret put TURNSTILE_SECRET`, не в Git и не в `VITE_*`.
4. `npm run db:migrate -- --remote`.
5. `npm run build:checked && npm run check:mail-config`, затем `wrangler deploy`.
6. Отправить явно помеченную тестовую заявку и проверить **три факта**: успешный ответ формы, запись D1, фактически полученное письмо в Gmail. Затем проверить Cron и отклонение некорректного запроса без письма.

Не переключать сайт на новую форму до подключения реальных ресурсов. `check:mail-config` блокирует сборку при пустом ID базы, пустом/тестовом публичном ключе, открытом секрете или флаге локальной разработки в production.

## Наблюдение и восстановление

Cloudflare → Workers → `mazganim-clean-air` → Observability: события `lead_saved`, `mail_accepted`, `mail_retry`, `lead_capacity`. Событие ошибки `outbox_stalled` означает неотправленные заявки старше 15 минут. Cron тоже должен запускаться и завершаться успешно. Уведомления мониторинга нужно настроить в аккаунте: запись в логе сама по себе не отправляет оповещение владельцу.

Очередь без персональных данных:

```sh
npx wrangler d1 execute LEADS_DB --remote --command "SELECT id, status, attempts, datetime(created_at/1000, 'unixepoch') AS received_utc, last_error FROM leads WHERE status != 'mail_accepted' ORDER BY created_at"
```

Контакты конкретной заявки безопаснее смотреть в закрытой D1 Console Cloudflare. Не вставлять вывод с персональными данными в публичные issues или CI-логи.

После исправления домена/секрета/почты Cron сам повторит отправку. Для немедленного повтора конкретной сохранённой заявки, заменив UUID на проверенный ID:

```sql
UPDATE leads SET status = 'pending', next_attempt = 0, lease_until = NULL, lease_id = NULL
WHERE id = 'UUID' AND status != 'mail_accepted';
```

Не запускать ручной повтор одновременно с действующей отправкой: дождаться истечения `lease_until`. Для повторной доставки уже принятого почтовой службой письма сначала проверить Gmail и ID заявки, затем явно перевести именно эту запись в pending. Не очищать всю таблицу для устранения сбоя.

Сохранять резервные копии по необходимости и учитывать ограниченное окно D1 Time Travel на текущем тарифе. Возврат сайта к старой версии не должен удалять D1 или принятые заявки; Cron доставки нужно оставить активным до опустошения очереди.

## Локальные проверки

`npm run build:checked` включает проверку сайта на пяти языках и SQL/Worker тесты на настоящем SQLite. Тестируются ограничения ввода и Origin, Turnstile, сбои D1/почты, повтор после потери ответа, конкурирующие запросы, восстановление зависшей отправки и сохранность неотправленных заявок.

Для локального Worker нужны отдельные `.dev.vars` с официальными тестовыми ключами Turnstile и `LOCAL_DEVELOPMENT=true`, затем локальная миграция D1. Этот флаг действует только на localhost/127.0.0.1 и не отключает проверку `success`. Тестовые ключи не должны попасть в production.
